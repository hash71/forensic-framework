Part 1 — Crash course (the 9 ideas the whole talk rests on)

1. Private cloud. A company running its own servers and storage (banks, government, hospitals) instead of renting from Amazon/Google. Important because public clouds (AWS, etc.) give you one neat "audit log" of everything; a private cloud does not — the evidence is scattered across many separate systems.
2. Forensic triage (post-incident). Forensics = investigating after something bad happened. Triage = the quick first pass that sorts "is this an attack or not, and who did it?" We are not doing real-time alarms; we're reconstructing what happened from logs already collected. Think detective, not burglar alarm.
3. Logs / events. Every action on a computer system gets recorded as a line in a log: "user X logged in at 9am", "user Y downloaded file Z". We call each line an event. Our system pulls events from 7 sources (logins, file access, admin actions, network, database, web, email) and puts them in one common format.
4. Rule engine (the "old" way / our baseline). A list of fixed if-then rules a security team writes, e.g. "IF more than 5 downloads in 30 minutes THEN alert." This is what industry uses today (called a SIEM). It's transparent and fast but brittle: it cries wolf on innocent activity and misses slow attacks spread over days.
5. LLM (Large Language Model). An AI like ChatGPT — here an open-weight model called Gemma that we can run on our own servers. It can read all the events and reason about them in a way rules can't. Open-weight matters because the forensic data never has to leave the company.
6. Hallucination. The core danger with LLMs: they sometimes make things up — invent an event or accuse a user that isn't in the evidence. In forensics, where every claim might go to court, that's unacceptable.
7. Evidence grounding + the validator (our key idea). We force the LLM to attach a specific event ID to every claim it makes ("user_03 did X — see event evt_s4_002"). Then a separate deterministic validator checks every cited ID against the real evidence. If the LLM cites something that doesn't exist, we catch it. This is the heart of the paper.
8. Calibration vs holdout (how we test fairly). We tuned the system on 15 scenarios (calibration). Then we tested it on 100 fresh scenarios it had never seen (holdout), generated automatically so we couldn't secretly bias them. Reporting holdout results is the honest, scientific way — like studying from practice problems but being graded on a new exam.
9. The result in one sentence. The LLM catches every attack (100% recall) but also over-accuses innocent users a lot (many false positives). Grounding stops it from inventing evidence, but it does not stop it from drawing the wrong conclusion from real evidence. So: useful as a high-recall assistant a human reviews — not an autonomous judge.
If you remember nothing else: "We make the AI cite its evidence and we check the citations. It finds every attack but over-flags innocent activity. So it's a first-pass assistant, not a replacement for a human or for rules."

2The problem — evidence is everywhere and nowhere

What's on screen

Seven cards (auth, file access, admin, network, database, web, email) and a big dark "0" card saying "0 unified audit planes — no CloudTrail in a private cloud."

Plain English

When a private company gets hacked, the clues are spread across seven separate systems with no single place to see them. Public clouds have a tool (CloudTrail) that unifies this; private clouds have nothing. Investigators stitch it together by hand — slow and error-prone.

When an incident hits a private cloud, the evidence is scattered across seven different log sources — logins here, file activity there, network traffic somewhere else. Unlike Amazon's cloud, there's no single audit view. Someone has to manually piece it together. That's the bottleneck we attack.
"Why not just use a public-cloud tool?" → Because regulated organizations — banks, government — legally can't put their data on someone else's cloud. They run their own, and the tooling there is far weaker.
3Two failing approaches

What's on screen

Two columns. Left (amber) = Rule-based / SIEM: transparent but brittle, floods alerts, misses slow attacks. Right (purple) = Unconstrained LLM: powerful but hallucinates, can't be trusted in court.

Plain English

The two obvious options each have a fatal flaw. Rules are trustworthy but dumb. A raw LLM is smart but untrustworthy. We want the smart of the LLM with the trustworthy of rules.

Today you've got two choices. Rule engines — the industry standard — are transparent and auditable, but brittle: they drown analysts in false alarms and miss attacks spread over days. A raw LLM is the opposite: it can reason across all that, but it hallucinates evidence, which is a non-starter when claims have to hold up in a legal review. Our work is about getting the upside of the LLM without that risk.
4Our question and approach

What's on screen

The research question in a navy banner, then four numbered steps: 1 Normalize (7 sources → one format), 2 Correlate (build a timeline), 3 Analyze ×2 (rules and LLM see the same evidence), 4 Validate (check every citation).

Plain English

Our pipeline in four moves. The important fairness point: the rule engine and the LLM get the exact same evidence, so any difference is due to reasoning, not one of them having more information.

Our research question: can an LLM that's only allowed to reason over structured evidence — and must cite an event ID for every claim — beat a transparent rule baseline while staying traceable? The pipeline is four steps: normalize the seven sources into one format, correlate them into a timeline, run both the rules and the LLM on that same timeline, and finally validate every citation the LLM makes.
"Why give both the same input?" → Fairness. If the LLM wins, it's because it reasoned better, not because we fed it extra clues.

8Headline result — the asymmetry

What's on screen

Two confusion matrices (rules vs Gemma) and a table of accuracy by slice. Key cell: the LLM's "attack→benign" box is 0 (it never misses an attack), but its "benign→attack" box is 22 (it wrongly flags 22 of 44 innocent cases).

Plain English

A confusion matrix is a 2×2 grid: rows are the truth, columns are the guess. You want the diagonal big and off-diagonal zero. The story: the LLM is perfect at catching attacks but over-flags benign activity. Overall accuracy (78% vs 70%) is not a statistically significant win — and we say so. The real finding is the asymmetry, not the average.

Here's the headline, and it's more interesting than a single number. Look at the LLM's confusion matrix: zero missed attacks — 100% recall. But it also flags 22 of 44 innocent cases as attacks. So overall it's 78% versus the rules' 70% — and honestly, at this sample size that gap isn't statistically significant. The real result is the shape: the LLM is a high-recall, low-precision detector.
"So it's not better?" → On overall accuracy, not significantly. But on catching attacks it's dramatically better (100% vs 70%, and that is significant). The trade-off is more false alarms. That's a useful, honest finding.
9Grounding holds at scale

What's on screen

Four stats: 99.95% citation validity (2067 of 2068 references were real), 0 fabricated event IDs, κ = 1.0 (perfectly repeatable verdicts over 110 reruns), and "abstains" under missing evidence.

Plain English

This proves the grounding actually works: across 115 scenarios the LLM essentially never cited fake evidence. κ (kappa) is a repeatability score — 1.0 means identical answers every rerun, which matters because people worry LLMs are random. And when we delete evidence, it says "insufficient" rather than inventing — the safe failure mode.

Does the grounding actually work? Yes. Across all 115 scenarios, 2067 of 2068 cited references were real events — 99.95%, zero fabricated IDs. And it's repeatable: 110 reruns, identical verdicts every time, kappa of 1.0. When we starve it of evidence, it abstains rather than guesses. So "zero hallucinated evidence" isn't a hope — it's measured.
"What's kappa?" → A standard agreement score from 0 to 1. 1.0 means perfectly consistent across repeated runs — it answers the "but LLMs are random" worry.
10Failure case 1 — S14, the decoy

What's on screen

A timeline: a loud decoy attacker (user_04) making lots of noise, and a quiet real attacker (user_02) stealing data in the background. The LLM blamed the decoy. A red box: "Grounding ≠ attribution."

Plain English

This is the paper's most important limitation, and we feature it. The LLM got the verdict right (yes, attack) but accused the wrong person — and every event it cited was real, so the validator stayed silent. Lesson: checking that citations are real does not guarantee the conclusion is right.

Now the honest part — where it breaks. In scenario 14 we planted a loud decoy and a quiet real attacker. The LLM correctly said "yes, attack" — but blamed the decoy, the wrong user. And here's the subtle bit: every event it cited was genuine, so the validator raised nothing. The lesson is the title of the slide: grounding guarantees the evidence is real, not that the conclusion drawn from it is correct.
"Isn't that bad for your paper?" → It's the opposite — reviewers trust papers that show their failures. And it points to the fix: make the model weigh alternative suspects before committing.
11Failure case 2 — S15, rule-context contamination

What's on screen

Left: with rule alerts in its prompt, the LLM said "attack" 5/5 times (wrong); without them, "not attack" 5/5 (correct). Right: "6 / 44" — testing more scenarios, this only flips 6 of 44, so it's a real but minor effect.

Plain English

Remember the dashed arrow on slide 5 — we feed rule alerts to the LLM. Here we test whether that's a good idea. Sometimes the alerts bias the LLM into agreeing with them even when the evidence doesn't support it. We proved it with an ablation (run it with and without and compare). It's a real effect but explains only a minority of the false positives.

Second failure. We feed the rule alerts to the LLM as context — is that safe? We tested it directly: with the alerts, it wrongly cried attack five times out of five; remove just the alerts, same evidence, and it correctly says no, five out of five. So rule output isn't neutral context — it can bias the model. But when we scaled the test to 44 scenarios, it only flipped 6, so it's a real but minor effect, not the main cause of the false positives.
"What's an ablation?" → Removing one ingredient and re-running to isolate its effect — here, removing the rule alerts from the prompt.

Part 3 — The 5 questions you'll most likely get

Q1. "Isn't 100% attack detection too good to be true — is it just saying 'attack' to everything?"
Fair worry, and partly true: it does lean toward "attack". But it's not blindly saying yes — on the clearly-normal baseline scenarios it correctly says no. The honest framing is what's on slide 8: very high recall, real false-positive cost. We don't hide that.
Q2. "Why only one LLM? Would Llama or GPT behave differently?"
That's our number-one limitation and it's on slide 14. The over-flagging might be specific to Gemma. Testing Llama and Mistral on the same corpus is the immediate next experiment — the code is built to swap models with one config change.
Q3. "Everything's synthetic — why should I believe it transfers to the real world?"
Two answers. One, the holdout is generated from an auditable recipe we couldn't bias. Two — and this is the strong one — slide 13: we ran it on CERT, real third-party insider data from CMU, and the same pattern got stronger. That's the opposite of overfitting to our own data.
Q4. "What exactly is new here? People already use LLMs for security."
Three things, together, that no prior work combines: (1) every claim must cite an event ID, checked by a deterministic validator; (2) we score verdict, suspect, and grounding as three separate things; (3) we design adversarial failure cases into the test set and keep them. The novelty is the rigorous methodology, not "an LLM does security."
Q5. "If the validator can't catch the wrong-suspect case (slide 10), what's it even for?"
It catches a different, very real danger: fabricated evidence — invented events, fake users. It does that with 99.95% reliability. Slide 10 just marks its boundary: it guarantees the citations are real, not that the interpretation is right. Knowing exactly where a safety mechanism stops is itself a contribution.

"Security investigators in private clouds drown in scattered logs. Rules are reliable but dumb; raw AI is smart but makes things up.
