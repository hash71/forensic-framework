So this is a genuine experimental artifact package. Now let me teach you what each piece actually does.
The one-paragraph version. Your project is a pipeline — a conveyor belt. Fake-but-realistic security logs go in one end. They get cleaned into one common format, sorted into a timeline, and then handed to two judges in parallel: a simple rule engine (the old industry way) and Gemma (the AI). Both answer the same question — "attack or not, and who did it?" The AI is forced to cite an event ID for every claim, and a separate validator checks those citations are real. Finally a statistics step scores both judges. That's the whole thing. The seven phases below are just the stations on that belt.

The conveyor belt

scenarios → normalize → timeline → ┬─ RULE ENGINE ──┐
                                    └─ GEMMA → VALIDATOR ┘ → EVALUATE → statistics

Phase 1 — Make the scenarios (the "fake crime scenes")

1115 scenario files, each a little story made of events

What it is

You couldn't use real company hack data (it's secret and unlabeled). So you built realistic incidents where you already know the right answer — like a teacher writing exam questions and the answer key. Each scenario is a JSON file: a list of events (log lines) plus a hidden ground-truth label (ATTACK or BENIGN).

A real event from scenario 4 (the slow-insider attack)

// data/scenarios/scenario_4.json — this is the actual first event
{
  "event_id": "evt_s4_001",
  "timestamp": "2026-04-01T09:00:00+06:00",
  "source_type": "auth",        // which of the 7 sources
  "user": "user_03",
  "action": "login",
  "source_ip": "192.168.1.103",
  "status": "success",
  "session_id": "sess_user_03_20260401_001",
  "severity": "info",
  "metadata": { "auth_method": "password" }
}

Scenario 4 has 27 such events spread over 3 days — user_03 slowly creeping from normal logins into reading finance files into downloading them. The label is ATTACK.

The 15 vs 100 split (this is important and clever)

  • 15 calibration scenarios (S1–S15) — hand-written by you. You tuned the AI's prompt against these. Think "practice problems."
  • 100 holdout scenarios — made by a generator (scenario_factory.py) from a recipe file with a fixed random seed. You never hand-edited them. Think "the real exam."

Reporting results on the holdout (the unseen 100) is the honest, scientific move — it proves you didn't just memorize your own practice questions.

Phase 2 — Normalize (make every source speak one language)

27 messy log formats → 1 clean format

The problem it solves

A login log, a database log, and an email log all look totally different in real life. If your two judges had to understand 7 different formats, the comparison wouldn't be fair. So normalizer.py rewrites all of them into the same shape — the "unified event schema" — the exact fields you saw above (event_id, timestamp, user, action, resource, source_ip, …).

Why it matters for fairness

Because of this step, the rule engine and Gemma read byte-for-byte the same evidence. When the paper says "any difference is reasoning, not extra information," this file is why that's true. It also tags each event with a severity and strips any hidden answer-key fields so they can't leak to the judges.

Phase 3 — The Rule Engine (your "old way" baseline)

312 fixed if-then rules — the industry-standard comparison

What it is

This is the thing the AI is being compared against. It's deliberately simple and transparent — a list of 12 rules in a plain config file. Here's a real one:

# config/rules.yaml — actual rule R004
- id: R004
  name: bulk_download
  severity: critical
  condition: count(file_download, window=30min) > 5

In English: "if one user downloads more than 5 files in 30 minutes, raise a critical alert." The 12 rules cover unusual logins, privilege escalation, bulk downloads, log deletion, DNS tunneling, etc. The engine runs them over the events and produces a list of alerts, then maps those to one verdict (any critical alert → "attack").

Its known weakness (which is the whole point)

It's dumb about context. It can't tell "5 downloads because the user is malicious" from "5 downloads because it's quarter-end and finance is busy." That brittleness is exactly what the AI is supposed to improve on.

Phase 4 — Run Gemma (the AI judge)

4The same evidence → the AI, with strict rules about citing

The ACTUAL prompt (not a guess — this is from the file)

# app/llm/prompts.py — the real system prompt, abridged
"You are a digital forensic analyst investigating a private
 cloud environment after a suspected security incident...

 STRICT RULES:
 1. Only reason about events explicitly listed in the timeline.
 2. Do NOT assume, invent, or infer events not present.
 3. If evidence is insufficient, say INSUFFICIENT EVIDENCE.
 4. Reference specific event_ids for every claim.
 5. Assign confidence: HIGH, MEDIUM, or LOW to each claim."

Rules 2 and 4 are the anti-hallucination heart: it may only talk about events it was given, and it must cite an ID for everything. The prompt also coaches it (rules 6–11) on traps the rule engine fails: failed logins aren't a breach, maintenance can look scary but be fine, lots of alerts ≠ attack, watch for slow insiders.

Crucial fact: no training happened

Gemma was used as-is, off the shelf, at temperature 0.1 (low = consistent answers). No fine-tuning, no LoRA, no reinforcement learning — I searched the code and found none. Everything the model "knows" about your task comes from that prompt. This is a prompting study, and the paper says so honestly.

Phase 5 — The Validator (the lie detector)

57 deterministic checks on every AI answer

What it does

This is your paper's signature contribution. After Gemma answers, hallucination_checker.py goes through its claims and asks, mechanically (no AI involved — pure code, so it's trustworthy):

  • Does every cited event_id actually exist in the evidence? catches invented events
  • Is the named suspect a real user from the logs? catches invented people
  • Do cited IP addresses / files appear in the evidence? catches invented entities
  • Are the cited events in sensible time order? Plus 3 more (uncited claims, time claims, volume claims).

Real output for scenario 3

// from evaluation_results.json, scenario 3
total citations: 23   valid: 23   invented: 0

Across all 115 scenarios this came to 2067 of 2068 citations valid (99.95%). That number is the proof that "the AI cites its evidence and the evidence is real."

The honest limit (your S14 slide)

The validator checks that citations are real — not that the conclusion is right. In scenario 14 the AI cited all-real events but blamed the wrong person. The validator can't catch that, and your paper says so plainly. Knowing exactly where your safety net stops is itself a contribution.

Phase 6 — Evaluation & statistics (the scoreboard)

6Compare the two judges to the answer key, with real statistics

What it computes

evaluator.py compares each judge's verdict to the hidden ground-truth label, and run_statistics.py turns that into the paper's tables: accuracy, recall (did we catch attacks?), false-positive rate (did we over-accuse?), citation validity, plus proper statistics — confidence intervals and the McNemar test (which asks "is this difference real or just luck?").

Trace one number so you trust the chain

The paper's calibration row says rules 66.7%, Gemma 86.7%. I recomputed it live from the raw answer files:

The numbers in the paper are not typed by hand — they're computed from the stored answers. That's what makes it reproducible.

The headline (from the 100 unseen holdout)

Rules 70% vs Gemma 78% overall (not a statistically significant gap, and the paper admits it). The real story is the split: on attacks Gemma gets 100% vs 70%; on benign cases it's worse than rules (50% vs 70%). High recall, low precision.

Phase 7 — CERT replay (the real-world test)

7Run the whole pipeline on real third-party data

Why this exists

The obvious criticism of phases 1–6 is "you made up your own data." So you took CERT r4.2 — a famous insider-threat dataset built by Carnegie Mellon, with real labels you didn't create — and ran the same pipeline on it. cert_insider.py maps CERT's 5 streams (logon, device, file, email, http) into your unified schema, then bundles each suspect's month of activity into a "window."

What actually happened (verified, including the messy parts)

  • 40 windows attempted, 35 scored, 5 lost to a server timeout — reported honestly, not faked.
  • The same pattern appeared and got stronger: caught all 20 real insiders, over-flagged nearly every innocent month.
  • Important caveat (in the paper and on slide 13): on this richer data Gemma returned Markdown prose instead of JSON in 34 of 35 windows. Verdicts were parsed from the prose. The validator could only run fully on the 1 JSON answer — so CERT is a verdict result, not a grounding result. You disclose this rather than hide it.

This is the strongest part of the paper precisely because the result survived data you never touched — and because you reported its warts.

The big picture — what to take away

  • It's a pipeline, not a model. You didn't build or train an AI. You built a careful harness around an off-the-shelf AI that forces it to cite evidence and then checks the citations.
  • The contribution is the method, not "an LLM did security." Per-claim citation + a deterministic validator + scoring verdict/suspect/grounding separately + keeping the failure cases — that combination is what's new.
  • The finding is honest and interesting: the AI is a high-recall, low-precision first-pass assistant. It catches everything but over-accuses. So it belongs next to rules and under a human, not replacing either.
  • Everything is real and reproducible. ChatGPT's worry — "maybe these experiments were never run" — does not apply. The files, the answers, the statistics all exist and trace to each other.
