1 Problem Statement

When a cyberattack hits an organization running private cloud infrastructure (VMware vSphere, OpenStack, etc.), investigators must reconstruct what happened from scattered, heterogeneous logs across hypervisors, VMs, network devices, and applications.

Current Problems
  • Logs are siloed — ESXi, guest OS, auth, file access, and network logs are all separate systems
  • No unified forensic timeline exists by default in private cloud environments
  • Public cloud has tooling; private cloud does not — AWS has CloudTrail/GuardDuty; VMware has nothing comparable
  • Existing tools are fragmented — DFIR4vSphere, QELP, ESXimager each handle one piece but don't correlate
  • Forensic evidence is sensitive — regulated industries cannot send logs to third-party LLM APIs
  • Manual reconstruction is slow, error-prone, and depends on scarce expert availability

2 Research Question

Does a locally-deployed open-weight LLM improve post-incident forensic understanding when given structured, correlated evidence from private cloud environments — without introducing unacceptable errors?

3 Research Contributions

Contribution 1: Multi-Source Log Correlation Engine

Ingests logs from multiple private cloud layers (hypervisor, VM, network, auth, file access) and normalizes them into a unified event schema for forensic analysis.

Contribution 2: Evidence-Grounded LLM Forensic Reasoning

Feeds structured, correlated evidence to a locally-deployed LLM for incident reasoning — constrained to only reason over provided evidence, preventing hallucination.

Contribution 3: Privacy-Preserving Deployment

Demonstrates that a local open-weight model can perform structured forensic reasoning comparable to traditional methods, without data leaving the security boundary.

Contribution 4: Comparative Evaluation

Rigorous comparison of rule-based-only vs LLM-assisted investigation across controlled attack scenarios, measuring detection quality, hallucination rate, and narrative usefulness.

Key Observations

  • Cloud forensics is well-studied for public cloud (AWS/Azure) with native tooling and multiple frameworks. Private cloud (VMware/OpenStack) has only FROST (2013) as a dedicated framework.
  • LLM + forensics is active but general-purpose. ForensicLLM, DFIR-Metric, ProvSEEK all exist, but none target cloud environments specifically, and none address private cloud.
  • LLM alone underperforms rules. The 2025 standardized evaluation paper found ChatGPT performs worse than rule-based approaches. But the hybrid approach (rules + LLM reasoning on structured output) has not been tested.
  • All AI forensic tools use cloud APIs. ForensicLLM is the only local model, but it's general-purpose, not designed for incident investigation or cloud evidence.
  • VMware forensic tools are fragmented. DFIR4vSphere (collection), QELP (parsing), ESXimager (acquisition) each do one thing. No unified correlation + timeline + analysis pipeline exists.

Three Gaps Your Research Fills

Gap 1: No Unified Private Cloud Forensics

Tools exist individually but nobody has built a unified correlation and timeline system tying hypervisor + VM + network + auth logs together.

Gap 2: No Local AI for Forensic Investigation

Every AI forensic tool (Security Copilot, Charlotte AI, Chronicle) requires sending data to cloud APIs. Regulated industries cannot use any of them.

Gap 3: No Rule vs LLM Forensic Comparison

Literature shows LLMs alone perform worse than rules. But the hybrid approach — rules + LLM reasoning on structured output — has never been tested.

Critical Finding from Literature

The 2025 paper "Towards a Standardized Methodology for Evaluating LLM-Based Digital Forensic Timeline Analysis" found that ChatGPT performs WORSE than rule-based approaches when used alone. This strengthens your research — your hybrid architecture (rules + LLM reasoning on structured output) is the approach nobody has tested yet.

9 LLM Prompt Design

Core Constraint
The LLM NEVER sees raw logs. It receives pre-processed, structured forensic input only. This is non-negotiable.

Input Template

You are a digital forensic analyst. Analyze the following
structured evidence from a post-incident investigation.

RULES:
- Only reason about events explicitly listed below.
- Do NOT assume or invent events not present in the evidence.
- If evidence is insufficient, say so explicitly.
- Assign confidence levels: HIGH, MEDIUM, LOW.

CORRELATED TIMELINE:
{timeline_json}

TRIGGERED RULES:
{rules_json}

ANOMALY INDICATORS:
{anomaly_json}

USER BASELINE:
{baseline_json}

TASK:
1. Is there evidence of a security incident? (YES / NO / INSUFFICIENT)
2. If YES, reconstruct the probable attack chain using only provided events.
3. Identify the most suspicious user and explain why.
4. List specific events (by event_id) that support your conclusion.
5. Note any gaps in evidence that limit your analysis.

What the LLM Must NOT Do

  • Invent timestamps or events not in the input
  • Assume network connections not present in logs
  • Speculate about attacker identity beyond evidence
  • Fill gaps with assumptions
